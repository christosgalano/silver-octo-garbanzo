# AWS base environment

Terraform for a small AWS base environment, and the pipeline that guards it. Misconfigurations such as world-readable buckets, SSH open to the internet or roles without a permissions boundary fail in CI, before a reviewer has to spot them and before anything is applied.

What it provisions per environment:

- **Network:** a VPC across two AZs with public and private subnets. The private tier has no route to the internet; it reaches AWS through VPC endpoints.
- **Public instance:** EC2 in a public subnet behind an Elastic IP, serving HTTP (nginx). Ports 80 and 443 are open to the internet.
- **Private instance:** EC2 in a private subnet. No inbound rules, no SSH key, no internet. Operated through Session Manager.
- **Artefacts bucket:** private, versioned, SSE-KMS, TLS-only. For build artefacts and logs.
- **Private instance role:** read access to the artefacts bucket and nothing else.

## Layout

```text
bootstrap/                    account setup, applied once per account
terraform/
  modules/                    reusable building blocks: network, instance, bucket
  stacks/base/                wires the modules into one environment
  live/<env>/                 per-environment config: backend, provider, terraform.tfvars
policy/terraform/             Rego policies and tests, evaluated by conftest on the plan
.github/
  workflows/ci.yaml           pull requests: checks, tests, scans, plan, policy, one gate
  workflows/cd.yaml           main: plan, policy, approved apply
  actions/terraform-setup/    install Terraform, assume a role through OIDC, init
  actions/terraform-report/   plan/apply report for the job summary and PR comments
  scripts/changes.sh          decides which units to test and which environments to plan
scripts/configure-github.sh   GitHub variables, environments and branch ruleset
```

- **Environments are configuration only.** A folder under `live/` holds the backend key, provider settings and `terraform.tfvars`, and calls `stacks/base`. All wiring lives once in the stack, so environments differ only in values.
- **Modules are small and single-purpose.** Each has its own README (generated by terraform-docs) and its own tests.
- **No Terragrunt.** With thin environment roots, plain Terraform covers what's needed at this size. Terragrunt is worth it once there are many accounts or regions, or stacks that depend on each other's outputs.

## Getting started

### Prerequisites

- Terraform >= 1.10 (CI uses 1.16.4), AWS CLI v2, `gh`, `jq`.
- Admin credentials for the target AWS account, for the one-off bootstrap.
- Optional: `pre-commit install`, which runs fmt, terraform-docs, opa fmt/test and Trivy before each commit.

### 1. Bootstrap the account

```bash
cd bootstrap
cp terraform.tfvars.example terraform.tfvars   # set budget_alert_email
terraform init
terraform apply
```

This creates the account-level foundations:

| Resource | Purpose |
| --- | --- |
| State bucket `tfstate-acme-<account>` | Terraform state. Versioned, TLS-only, `prevent_destroy`, native S3 locking. |
| GitHub OIDC provider | Short-lived credentials for Actions; no access keys anywhere. |
| `gha-acme-plan` | Read-only plan role, assumable from pull requests and `main`. |
| `gha-acme-<env>-apply` | Apply role per environment, assumable only from that GitHub Environment. |
| `acme-workload-boundary` | Permissions boundary every pipeline-created role must carry. |
| Default Host Management Configuration | Session Manager access for every IMDSv2 instance, without SSM permissions in instance roles. |
| Budget | Monthly cost budget with email alerts. |

Bootstrap state is local and git-ignored.

### 2. Configure GitHub

```bash
scripts/configure-github.sh [reviewer-login]
```

| Scope | Variables / settings |
| --- | --- |
| Repository | `AWS_REGION`; per environment `<ENV>_AWS_ACCOUNT_ID`, `<ENV>_TF_STATE_BUCKET`, `<ENV>_AWS_PLAN_ROLE_ARN` (e.g. `DEV_*`) |
| `dev` environment | `AWS_APPLY_ROLE_ARN`; required reviewer; deployments from `main` only |
| Ruleset on `main` | PR required, no force pushes or deletion, `CI gate` must pass |

Plan jobs don't run in a GitHub Environment, so their per-environment settings are repository variables prefixed with the environment name. The apply role ARN lives on the environment, so only jobs that passed its gate can see it. Nothing in GitHub is a secret.

Enforced rulesets and environment reviewers on private repositories need a paid GitHub plan.

### 3. Day to day

Open a pull request. CI tests and plans what the change affects, and posts the plan and the policy result as a comment. After merge, CD plans `main` again and waits for approval on `dev`, then applies that exact saved plan.

Planning locally with your own credentials:

```bash
cd terraform/live/dev
terraform init -backend-config="bucket=tfstate-acme-<account-id>"
terraform plan
```

### 4. Tear down

```bash
cd terraform/live/dev && terraform destroy
```

There's no destroy workflow: destroying an environment is rare enough to be a deliberate, manual step. The bootstrap stays.

**Cost:** dev runs at roughly $45–50/month in eu-central-1, mostly the three SSM interface endpoints (~$26) and two t3.micro instances (~$17).

## Access to the private instance

Session Manager through VPC interface endpoints (`ssm`, `ssmmessages`, `ec2messages`), with no NAT gateway, no bastion and no SSH.

```bash
aws ssm start-session --target <private-instance-id>
```

- **No inbound path.** The SSM Agent connects outbound to the endpoints, so the instance needs no inbound rules and no open port.
- **Access is IAM.** Opening a session is an IAM permission (`ssm:StartSession`), with MFA, SSO and CloudTrail behind it. There are no SSH keys to distribute.
- **Clean instance role.** Session Manager credentials come from Default Host Management Configuration, so the instance role only reads the artefacts bucket (`s3:GetObject`, `s3:ListBucket`, and `kms:Decrypt` through S3). DHMC applies only while the instance profile doesn't grant `ssm:UpdateInstanceInformation`.
- **No internet.** The private route table has no default route, and S3 is reached through the gateway endpoint. The instance can't install packages from the internet; workloads that need software should ship it in the AMI.

| Alternative | Why not |
| --- | --- |
| Bastion host | Another internet-facing host to patch, SSH keys to manage, port 22 open somewhere. |
| Session Manager through a NAT gateway | Simpler, but gives the instance general internet egress. About $32/month plus data. |
| EC2 Instance Connect Endpoint | Free and IAM-gated, but still SSH (port 22 from the endpoint), and no session logging out of the box. |

Interface endpoints are billed per AZ. In dev they sit in the private instance's AZ only (`interface_endpoints_multi_az = false`). DHMC is a region-wide account setting, so it lives in `bootstrap/`; new instances can take up to 30 minutes to register.

## Guardrails

All of these run before anything is applied.

| Layer | When | What it catches |
| --- | --- | --- |
| `terraform fmt`/`validate`, tflint (AWS ruleset), terraform-docs check | every PR | Invalid or sloppy code, unknown instance types, stale module docs |
| `terraform test` (mocked provider) | PRs touching modules or stacks | Module contracts: private by default, IMDSv2, EIP only when public, permissions boundary on roles, input validation |
| Trivy (`trivy config`) | every PR, pre-commit | Generic AWS misconfiguration in the HCL. Any finding fails the job. |
| conftest (Rego in `policy/`) | PRs and CD, on the plan JSON | House rules, on resolved values |

Trivy knows AWS best practice and reads the HCL. conftest knows the house rules and reads the plan, so it sees values after variables, modules and `for_each` are resolved.

### Policies

| Area | Rules |
| --- | --- |
| Security groups | Ingress from `0.0.0.0/0` or `::/0` only on TCP 80/443 and only on rules tagged `Exposure=public`. Never 22 or 3389 from anywhere. Standalone rule resources only. |
| Instances | Approved instance types only. `Exposure` tag required. IMDSv2 required. No automatic public IPs. |
| IAM | Every role carries the workload permissions boundary. No `*` or `service:*` actions. No `*` principals in trust policies. Documents only known after apply produce a warning. |
| Tags | Taggable resources carry `Project`, `Environment`, `Owner` and `ManagedBy`. |

Policies are linted with Regal and unit-tested with `opa test`. CI fails below 90% coverage; it's currently 100%.

### Change-aware CI

`.github/scripts/changes.sh` compares the PR with its base:

| What changed | Tested | Planned |
| --- | --- | --- |
| `terraform/modules/<m>` | that module and every stack | every environment |
| `terraform/stacks/<s>` | that stack | every environment |
| `terraform/live/<e>` | nothing | that environment |
| `policy/`, `.github/`, `trivy.yaml`, `.tflint.hcl` | nothing | every environment |

Matrix jobs are skipped when nothing relevant changed, so the ruleset requires a single check, `CI gate`, which fails if anything it depends on failed or was cancelled.

### Plan and apply reports

Every plan (CI and CD) and every apply (CD) is reported the same way, in the job summary and as a sticky PR comment:

- the `Plan:` or `Apply complete!` line;
- the command that ran;
- one line per resource: create, update/replace, destroy, and any failures with their error;
- the full output, collapsed.

Refresh noise (`Reading...`, `Refreshing state...`) is left out.

## Plan and apply

- **Pull requests** plan with the read-only plan role and `-lock=false`, so a plan never blocks an apply.
- **CD** plans `main` again, re-runs conftest on that plan, and saves it. The apply job waits for approval on the `dev` environment, then applies the saved plan. If state changed in between, Terraform rejects the stale plan.

The approval is enforced twice:

- **In GitHub:** the environment's required reviewer and its `main`-only rule.
- **In AWS:** the apply role trusts only tokens for `environment:dev`. Trust conditions use GitHub's immutable subject claims (`repo:<owner>@<id>/<repo>@<id>:…`), so a renamed or re-created repository can't inherit them.

## Accepted findings

Suppressions are inline, directly above the resource and with a reason, so they appear in the same diff as the code they cover. There's no `.trivyignore`.

| Finding | Where | Reason |
| --- | --- | --- |
| `AWS-0104` egress to the internet | `stacks/base/compute.tf`, public web egress | The public instance needs OS packages and the SSM endpoint. Limited to 80/443. |
| `AWS-0089` no access logging | `modules/bucket/main.tf` | Needs a separate log bucket; CloudTrail data events are the better fit. **Expires 2027-03-31**, after which CI fails until it's revisited. |
| `AWS-0089` no access logging | `bootstrap/state.tf` | CloudTrail management events already record access to the state bucket. |
| `AWS-0132` SSE-S3, not a CMK | `bootstrap/state.tf` | Access is controlled by IAM; the plan role is denied object reads outside the state bucket. |

Also worth knowing:

- **conftest warnings** on `decrypt_artifacts` and the flow-log role policy: both reference ARNs that only exist after apply. The S3 ARNs in the instance role's policy are built from names, so that document stays checkable at plan time.
- **The public 80/443 ingress has no suppression.** Trivy's public-ingress check (AWS-0107) only covers SSH and RDP. The web-ports rule is enforced by conftest.
- **Trivy reads `terraform/live/dev/terraform.tfvars`** (set in `trivy.yaml`). Without it, anything that depends on root inputs is skipped quietly.
- **Regal `with-outside-test-context`** is ignored for `*_test.rego` only, where test helpers wrap `with`.

## Known limitations

- **No drift detection.** Console changes go unnoticed until the next plan.
- **The plan role runs PR code.** Providers and data sources execute during plan, so anyone who can open a PR can act as the plan role. It's read-only, can't read objects outside the state bucket, and can't decrypt or read secrets.
- **The apply role is broad within its services.** `ec2:*`, `kms:*` and `logs:*` are account-wide. IAM is fenced by name prefix and the permissions boundary, S3 by bucket prefix. That's fine for a dedicated account, not a shared one.
- **Policies see only the plan.** Values known only after apply aren't checked, and nothing here looks at runtime state (AMI patch level, application vulnerabilities).
- **No TLS termination.** 443 is open, but there's no domain or certificate.
- **Ruleset admins can bypass it**, by design, for break-glass.
- **No high availability.** One instance of each, in one AZ.
- **Root on the instances uses the Systems Manager role.** The SSM Agent shares its DHMC credentials through root's AWS credentials file, which comes before the instance profile in the SDK chain. Session Manager shells (`ssm-user`) and applications get the instance role.
- **Renaming `for_each` keys needs a `moved` block.** Without one, Terraform destroys and recreates the resources in parallel. For security group rules, the creates then fail as duplicates.

## Roadmap

1. Move bootstrap state into the state bucket, and plan `bootstrap/` in CI.
2. Session Manager preferences: session logs to S3/CloudWatch, idle timeout, non-root `run as`.
3. An ALB with ACM in front of the web tier, and the instance moved into a private subnet.
4. Scheduled drift detection: a nightly `plan -detailed-exitcode` that opens an issue.
5. One AWS account per environment under AWS Organizations, with SCPs, and tag-based conditions on the apply role.
6. conftest rules: instance profiles never grant `ssm:UpdateInstanceInformation`, and S3 public access blocks are complete.
7. `ShareCreds: false` in the SSM Agent config through user data.
8. Publish the policies as an OPA bundle for other repositories to consume.
